# Collaboration — 与 Kiro 协作的约定

## 信息分级（必须显式区分）

| 标记 | 含义 |
| --- | --- |
| **已核实** | 能指到官方规则原文、官方文档或本机实测输出 |
| **Alex 陈述** | Alex 本人提供的情况，未由外部原始证据独立验证 |
| **待核实** | 官方规则/外部事实尚不确定，或需要去官方渠道确认 |
| **待决定** | 产品/项目层面尚未做出的选择 |

不要把「Alex 陈述」写成「已核实」，不要把「待决定」写成「已定」，不要把讨论起点写成结论。

## 规则处理

1. **官方规则不确定的地方一律标记「待核实」，不要自行推测、补全、类比或用常识填空。**
2. 待核实项统一登记在 `context/open-questions.md`；规则条目统一维护在 `context/rules-verified.md`。不要在多个文件里各写一份，避免不一致。
3. 引用规则时尽量保留英文原文，并给出 `[n]` 来源编号或 `context/evidence/` 快照位置。
4. 引用官方数字、日期、金额时，先对照 `context/evidence/kiroween-rules-2026-11-13.txt`（2026-11-13 抓取快照）。规则可能更新，提交前须复核 rules 页。
5. 遇到歧义：如实说明分歧，不要挑一个「看起来合理」的解释当成规则。官方给出的渠道是截止前提交书面澄清请求。

## 产品决策

- 主题、产品方向、技术栈、平台、组队方式**均未定**。Kiro 应提问与给选项，不应默认替 Alex 选定。
- 任何选型都要落到 `decisions/DECISIONS.md`，写明状态（已定 / 待定 / 已否决）、理由与影响。
- 创意先记进 `ideas/IDEAS.md`，标注是线索、讨论起点还是已选方向。

## 敏感信息

- Kiro credits 一次性兑换链接、Devpost / Kiro 账号凭据、身份验证材料**绝不写入工作区文件**。
- 本目录未来会成为**公开 GitHub 仓库**；任何写入前先问「这个内容公开是否安全」。
- Gmail 邮件只保留索引与要点，不整封复制进仓库。

## 证据优先

- 报告「已验证」时说明：改了什么、用什么命令/方法验证、观察到什么、还有什么没验证。
- 不要用「测试全绿」「已完成」这类无输出支撑的表述代替证据。
- 本机环境为探测所得，不等于构建可用；选定技术栈后须真实跑一次构建。
